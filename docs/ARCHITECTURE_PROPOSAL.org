#+TITLE: CoreEQ Architecture Proposal
#+SUBTITLE: Layer-Based Equalizer Architecture
#+AUTHOR: Architecture Proposal
#+OPTIONS: toc:3 num:nil

* Vision

CoreEQ should expose one equalizer with multiple editing experiences.

Graphic EQ and Parametric EQ are not separate equalizers.

Instead, they are different editing layers contributing to a single frequency response.

Users should never think about conversions.

Users should never wonder which equalizer is currently active.

Instead, they should understand a very simple mental model:

"I have one equalizer composed of several layers."

Every layer contributes to the final sound.

The frequency response graph always represents the complete result.

* Design Principles

The architecture is based on the following principles.

** One preset

A preset represents one equalizer configuration.

** One DSP engine

Only one DSP engine exists.

** One frequency response

The graph always represents the complete DSP output.

** Additive editing

Every editing mode contributes additional processing.

Nothing is converted.

Nothing is destroyed.

Nothing changes identity.

** Progressive disclosure

Graphic editing is simple.

Parametric editing is powerful.

Advanced DSP features integrate naturally without changing the basic workflow.

* High-Level Architecture

#+begin_src text
Preset
│
├── Global Gain
│
├── Graphic Layer
│
├── Parametric Layer
│
├── System Layer
│
└── Metadata
        │
        ▼
    DSP Engine
        │
        ▼
Frequency Response
        │
        ▼
    Audio Output
#+end_src

The DSP engine processes every enabled filter from every layer.

Layers are purely organizational.

* Preset Model

#+begin_src text
Preset
{
    UUID

    Name

    Description

    GlobalGain

    GraphicLayer

    ParametricLayer

    SystemLayer

    Metadata
}
#+end_src

The preset contains no "Graphic EQ" object.

It contains no "Parametric EQ" object.

Instead it contains processing layers.

* Layer Architecture

Each layer has a different responsibility.

Layers are independent.

Layers never replace one another.

Layers are additive.

** Graphic Layer

The Graphic Layer is the beginner-friendly editor.

It always contains the predefined ISO frequency bands.

Example:

#+begin_src text
32 Hz

64 Hz

125 Hz

250 Hz

500 Hz

1 kHz

2 kHz

4 kHz

8 kHz

16 kHz
#+end_src

Each band contains:

#+begin_src text
Frequency

Gain
#+end_src

Frequency is fixed.

Q is fixed.

Filter type is fixed.

Only gain is editable.

Graphic Layer is always present.

Its structure never changes.

** Parametric Layer

Initially the Parametric Layer is empty.

#+begin_src text
Parametric Layer

(empty)
#+end_src

The user may create any number of filters.

Examples:

- Bell
- Low Shelf
- High Shelf
- High Pass
- Low Pass
- Notch
- Band Pass

Each filter contains:

#+begin_src text
Type

Frequency

Gain

Q

Enabled
#+end_src

The Parametric Layer never modifies the Graphic Layer.

It simply adds more processing.

** System Layer

System Layer contains automatically generated DSP processing.

Examples:

- Headphone correction
- AutoEQ
- Device calibration
- Loudness compensation
- Hearing compensation
- Room correction
- FIR convolution
- Safety limiter

These filters are managed by CoreEQ.

Users normally enable or disable features instead of editing individual filters.

Future DSP functionality should be implemented inside the System Layer whenever possible.

* DSP Pipeline

The DSP engine is intentionally simple.

#+begin_src text
Graphic Layer

+

Parametric Layer

+

System Layer

↓

Enabled Filters

↓

DSP Engine

↓

Frequency Response

↓

Audio Output
#+end_src

The DSP engine has no knowledge of editing modes.

It simply processes filters.

* Editing Modes

Editing modes are user interface concepts.

They never affect the DSP architecture.

** Graphic Mode

Graphic Mode edits only the Graphic Layer.

The user edits:

- Gain

The user cannot edit:

- Frequency
- Q
- Filter Type

Graphic Mode is intentionally simple.

It always displays the same set of sliders.

Nothing disappears.

Nothing changes identity.

The graph always displays the complete response generated by every layer.

** Parametric Mode

Parametric Mode edits only the Parametric Layer.

Initially no filters exist.

The user explicitly creates filters.

Example workflow:

#+begin_src text
Open Parametric

↓

Empty list

↓

+ Add Filter

↓

Bell

↓

180 Hz

↓

+3 dB

↓

Q 0.8
#+end_src

The Graphic Layer remains untouched.

The graph immediately reflects the new filter.

* Layer Interaction

Layers are additive.

Example.

Graphic Layer:

#+begin_src text
125 Hz

+3 dB
#+end_src

Parametric Layer:

#+begin_src text
Bell

180 Hz

+2 dB
#+end_src

Result:

Both filters are processed.

Neither replaces the other.

Nothing is converted.

Nothing is disabled.

Both remain editable forever.

* Example Workflow

Preset:

#+begin_src text
Graphic Layer

125 Hz

+2 dB
#+end_src

Graph:

#+begin_src text
      /\
_____/  \_____
#+end_src

User opens Parametric Mode.

The Parametric Layer is empty.

User creates:

#+begin_src text

#+end_src

Graph becomes:

#+begin_src text

#+end_src

Returning to Graphic Mode:

The Graphic Layer remains unchanged.

The 125 Hz slider still exists.

It still controls only the Graphic Layer.

The graph still displays the combined response.

* Why Layers Instead of Conversion

Traditional approaches attempt to convert between Graphic EQ and Parametric EQ.

This introduces difficult questions.

Examples:

- Which filter owns the sound?
- What happens when frequency changes?
- Can the Graphic sliders still represent the DSP?
- How is reverse conversion performed?

Layering removes every one of these questions.

Graphic editing remains Graphic editing.

Parametric editing remains Parametric editing.

Both simply contribute processing.

* Advantages

** No conversion

Nothing is ever converted.

** No synchronization

Graphic and Parametric editors never synchronize.

They edit independent layers.

** Stable UI

Graphic Mode always contains the same sliders.

Nothing disappears.

Nothing changes identity.

** Deterministic

Every edit has a predictable result.

No optimization.

No approximation.

No hidden algorithms.

** Extensible

Future DSP features naturally become additional System Layer processing.

Examples:

- AutoEQ
- Headphone correction
- FIR convolution
- Room correction
- Loudness
- Hearing correction

No architecture changes are required.

* UI Philosophy

The graph is the visual truth.

The controls are editing tools.

Changing tabs never changes:

- preset
- graph
- DSP
- audio

Only the editing tools change.

Graphic Mode should feel approachable.

Parametric Mode should feel professional.

System processing should integrate without overwhelming users.

The complexity of the application grows through additional layers rather than replacing existing functionality.

* Guiding Principle

CoreEQ should never ask:

"Should this be Graphic EQ or Parametric EQ?"

Instead it should ask:

"Which processing layer should own this filter?"

Graphic processing remains simple.

Parametric processing remains powerful.

System processing remains automatic.

Together they produce one deterministic frequency response through one DSP engine.

The user experiences one equalizer composed of multiple independent processing layers.

This architecture minimizes surprises, scales naturally with future DSP features, and follows a non-destructive editing philosophy similar to modern creative applications such as Apple Photos, Logic Pro, and Adobe Photoshop.
