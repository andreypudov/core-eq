#+TITLE: CoreEQ — Feature Requests from User Comments
#+DATE: <2026-08-02 Sun>

Analysis of the questions and requests in [[file:USER_COMMENTS.org][USER_COMMENTS.org]], grouped by how often
they came up and how much they block everyday use. Fourteen comment threads
were reviewed; the ones that carry no request (praise, trivia, unrelated
plugs) are omitted.

* Tier 1 — asked repeatedly or blocking normal use

** Parametric bands: custom centre frequency and bandwidth

Three separate threads. The single most requested change.

- “Any chances to modify the frequency per band, the bandwidth …”
- “Do you have plan for custom frequency?”
- Raised again indirectly in the curve-ripple thread, where fixed one-octave
  bells at fixed centres are the cause of the sag.

Today =BuiltInProfiles.frequencies= is a fixed eleven-entry ISO ladder and
=defaultQ= is a constant 1.41. =EQBand= already carries per-band =frequency=
and =q=, and =PeakingFilter= already takes both — so the DSP side is largely
in place; the work is UI, preset schema, and migration.

** Global gain / preamp

One thread, but stated as a usability blocker rather than a wish:

- “To make this usable for normal people you really need to have global gain
  setting. Modern mixing hardly has headroom for +6 bass etc.”

There is no preamp anywhere in =EQProcessor= or =AudioEngine= today. Any
positive band gain eats source headroom directly. Worth pairing with an
auto-trim that pulls output back by the peak of the computed curve.

* Tier 2 — clear asks, single mention

** Homebrew distribution

- “I think distribution through homebrew would give a major boost”

Packaging and update path, not a code change. Currently the Makefile builds a
local Release app only.

** Linear-phase processing

- “Any chances to modify … and linear phase?”

A second processing mode alongside the current biquad cascade. Significant
work: FIR design, latency, and a latency-aware tap path.

** Inter-band ripple / summing behaviour

- “My concern would be that this sag was audible in some cases? I don’t know
  how other equalizers do that to eliminate interpolation artifacts”

Follows from the fixed Q of 1.41 at octave spacing. Largely resolved by Tier 1
bandwidth control, but worth an explicit decision on the default so the stock
curve sums flatter out of the box.

** Visual design of the response plot

- “What's with the graphics, the green lines and markers are plain weird?”

=Theme.accent= is hardcoded to System Green. Options raised in reply: follow
the system accent colour, or tone the green down. No specifics from the
commenter yet on which element reads worst.

** AutoEQ integration

- “AutoEQ + this would be awesome”

Import of AutoEQ headphone-correction profiles. Depends on Tier 1 — AutoEQ
targets need arbitrary centre frequencies and Q values, plus a preamp value,
so it is not implementable against the fixed ladder.

* Tier 3 — noted, out of current scope

** iOS version

- “Are you working on a version for iOS? Been desperate for this!!”

Declined for now on resource grounds. Also a different capture story
entirely — the process-tap API is macOS-only.

* Cross-cutting observation

Four of the requests above — parametric bands, linear phase, AutoEQ import,
and ripple control — all point at the same underlying change: moving from a
fixed eleven-band graphic EQ to a configurable filter chain. Doing the band
model first unblocks the rest.
