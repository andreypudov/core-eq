#+TITLE: CoreEQ — Developer Guide

Everything needed to build, run, test, and package CoreEQ, plus a tour of the
project structure and architecture. End-user documentation is in
[[file:../README.org][README.org]].

* Toolchain

- Xcode *16 or later* (the project uses the folder-synchronized project
  format, =objectVersion 77=).
- macOS *14.2 or later* to run (the process-tap API does not exist earlier).
- No external dependencies — system frameworks only (SwiftUI, AppKit,
  CoreAudio, AudioToolbox, Combine, os).

If your active developer directory points at the Command Line Tools instead of
Xcode (=xcode-select -p= prints =/Library/Developer/CommandLineTools=), either
switch it once:

#+begin_src sh
sudo xcode-select -s /Applications/Xcode.app
#+end_src

or prefix every =xcodebuild= call with
=DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer=.

* Building

Open =CoreEQ.xcodeproj= in Xcode and build (⌘B), or from the command line:

#+begin_src sh
xcodebuild -project CoreEQ.xcodeproj -target CoreEQ -configuration Debug build
#+end_src

=make build= does the same for the Release configuration (see “Packaging and
releases” for all Makefile targets).

The app lands in =build/Debug/CoreEQ.app=. The build is ad-hoc signed
(=CODE_SIGN_IDENTITY=-=) with the hardened runtime disabled — fine for local
development, revisit for distribution (see “Packaging”).

* Running

#+begin_src sh
open build/Debug/CoreEQ.app
#+end_src

- CoreEQ is a menu bar app (=LSUIElement=): no Dock icon, look for the sliders
  icon in the menu bar.
- First launch triggers the macOS *System Audio Recording* permission dialog.
  The explanation shown in it is the usage string in =Config/Info.plist=
  (=NSAudioCaptureUsageDescription=), which is macOS's own mechanism for saying
  what a permission is for at the moment it is asked for.
- Refusing does *not* fail loudly. =AudioHardwareCreateProcessTap= returns
  success even when the permission was refused: the tap reports a plausible
  format, the aggregate runs, the IO proc fires, and every sample is zero. See
  *Proving the tap* below for what the engine does about it.
- Note that TCC ties the permission to the code signature; rebuilding with a
  different signature may re-prompt.

Engine activity is logged through =os.Logger= (subsystem
=com.andreypudov.coreeq=). Follow it live with:

#+begin_src sh
log stream --predicate 'subsystem == "com.andreypudov.coreeq"' --level info
#+end_src

* Testing

=make test= runs =CoreEQTests=, a host-less logic bundle covering the filter
maths, the built-in profiles, =ProfileManager=, =SettingsStore=, the analyzer and
its ring buffer, the scroll handling, and the layout arithmetic that has no
runtime check. See “Packaging and releases → Tests” for how the target is
assembled.

Nothing in that suite touches audio hardware, so the parts that only exist at
runtime still need a manual pass after changes:

1. Build and launch; confirm the menu bar icon appears and the window's header
   shows no engine warning.
2. Play music; switch between *Flat* and *Bass Booster* — the change must be
   audible, immediate, and free of clicks.
3. Toggle the master switch — instant, glitch-free.
4. Drag a band slider — the sound tracks the slider smoothly and the curve
   follows it.
5. Switch the system output device (speakers → headphones) — processing resumes
   on the new device within ~1 s, *and that device's own preset loads*.
6. Quit and relaunch — preset, edits, and enabled state come back, per device.
7. Quit — system audio returns to the normal unprocessed path.

* Packaging and releases

The =Makefile= wraps the common flows (it also auto-selects the full Xcode
toolchain if =xcode-select= points at the Command Line Tools):

| =make build=   | Release build into =build/Release/CoreEQ.app=          |
| =make test=    | Run the =CoreEQTests= unit suite                       |
| =make format=  | Apply the house style to every Swift file              |
| =make lint=    | Report style violations without changing anything      |
| =make install= | Build and install to =/Applications=                   |
| =make release= | Build and zip to =dist/CoreEQ-<version>.zip= (=ditto=) |
| =make clean=   | Remove =build/= and =dist/=                            |

*** Tests

=CoreEQTests= is a host-less logic bundle: it never launches the app or touches
audio hardware, so it runs anywhere, including CI. Roughly one file per subject:

- =BiquadTests=, =EQProcessorTests=, =AutoGainTests= — the maths, and what the
  render path does with it.
- =FilterChainTests=, =PresetLibraryTests=, =EQProfileTests= — the model as value
  types, without a manager.
- =ProfileManagerTests= — the live state: editing, presets, tone.
- =DeviceStateTests= — what is remembered: per device, across a relaunch, and
  between A and B.
- =SettingsStoreTests=, =ThemeTests=, =ScrollAdjusterTests=, =KnobScaleTests=,
  =SpectrumAnalyzerTests=, and the small format and colour files.

*A warning about the runner.* =make test= builds incrementally, and a file
rewritten quickly enough can be missed — the suite then runs and passes without
the tests you just added. The count is the check: if the total does not move,
the run is lying to you. =touch= the file and run again.

Because the project uses =PBXFileSystemSynchronizedRootGroup=, the test target
takes the whole =CoreEQ/= folder *minus* an exclusion list. A new source file
joins the test target automatically — if it imports SwiftUI, AppKit, or
CoreAudio, add it to =membershipExceptions= in =project.pbxproj= or the test
build will fail. Those entries are paths relative to =CoreEQ/=, so they carry
the folder too (=UI/MenuBar/MenuBarController.swift=); moving a file between
folders means updating its entry.

** Cutting a release

CoreEQ is distributed unsigned (ad-hoc signature, no Apple Developer
account). The release pipeline is GitHub Actions
(=.github/workflows/release.yml=): pushing a tag matching =v*= builds
=make release= on a macOS runner and attaches the zip to a GitHub Release
with generated notes.

*The runner image is a user-visible choice.* AppKit decides which generation of
the macOS design an app renders in from the SDK it was *linked against*, not
from the macOS running it. Building 1.6 on the =macos-15= image (Xcode 16, SDK
15.5) shipped a binary that drew as a pre-26 app on every current Mac, while
local builds against the 26 SDK looked native — same commit, same version, two
different-looking apps. Both workflows therefore pin =macos-26=, and the release
job asserts the linked SDK out of =LC_BUILD_VERSION= before publishing. The
deployment target (=MACOSX_DEPLOYMENT_TARGET= 14.2) is set in the project and is
unaffected by any of this: a 26-SDK build still runs on macOS 14.2.

1. Bump =MARKETING_VERSION= (and =CURRENT_PROJECT_VERSION=) in the target
   build settings.
2. Commit, then tag and push:
   #+begin_src sh
   git tag v1.1
   git push origin v1.1
   #+end_src

Notes on unsigned distribution:

- Downloaded (quarantined) copies trigger Gatekeeper; users bypass it once
  via System Settings → Privacy & Security → *Open Anyway* or by clearing
  the quarantine attribute. Building from source avoids this entirely —
  local builds are never quarantined. Both paths are documented for users
  in [[file:../README.org][README.org]].
- The System Audio Recording (TCC) permission is keyed to the code
  signature; ad-hoc signatures have no stable identity, so each shipped
  update re-prompts users for the permission.

** If a Developer ID account becomes available

Sign with hardened runtime and notarize; this removes the Gatekeeper
warning and the per-update permission re-prompts:

#+begin_src sh
xcodebuild -project CoreEQ.xcodeproj -target CoreEQ -configuration Release build \
  CODE_SIGN_IDENTITY="Developer ID Application: Your Name (TEAMID)" \
  ENABLE_HARDENED_RUNTIME=YES

ditto -c -k --keepParent build/Release/CoreEQ.app CoreEQ.zip
xcrun notarytool submit CoreEQ.zip --keychain-profile <profile> --wait
xcrun stapler staple build/Release/CoreEQ.app
#+end_src

The app is currently *unsandboxed*. App Store distribution would require
enabling the sandbox and revisiting the audio entitlements; direct
(Developer ID) distribution does not.

* Build settings that matter

Beyond the Xcode template's defaults, four are set deliberately.

- *=SWIFT_VERSION = 6.0=* — the Swift 6 language mode, which makes data-race
  safety a compile-time property rather than a hope. It matters more here than in
  most apps: everything is =@MainActor= except =EQProcessor.render=, which Core
  Audio calls on a realtime thread, and the compiler now checks that boundary
  rather than trusting the comments around it.

  The migration cost two =deinit= fixes. =SpectrumAnalyzer= and =AudioDeviceList=
  both cleaned up main-actor state from a nonisolated =deinit= — a `Timer` bound
  to a run loop, a vDSP allocation, and Core Audio listener blocks — which can
  run on any thread. Both are =isolated deinit= now, which is the honest
  statement: that cleanup belongs to the main actor.

- *=SWIFT_TREAT_WARNINGS_AS_ERRORS = YES=* — the codebase had no warnings, so
  this cost nothing to adopt and everything to skip. It immediately caught two
  =var= bindings in tests that were never mutated.

- *=SWIFT_UPCOMING_FEATURE_EXISTENTIAL_ANY = YES=* — =any Decoder= rather than
  bare =Decoder=. Required by a future language mode anyway; six call sites.

- *=VALIDATE_PRODUCT = YES=* (Release only).

*One thing measured and rejected.* =SWIFT_STRICT_MEMORY_SAFETY= produces 244
findings, almost all in the audio path, where =UnsafePointer= work is the job
rather than a mistake: the IO proc is handed raw buffers by Core Audio and must
not allocate. Adopting it would mean annotating that code =@unsafe= to say what
is already true, and the ratio of noise to insight is wrong. =MemberImportVisibility=
is the same story at 38 findings, for less benefit.

*A compiler bug worth remembering.* Passing an actor-isolated closure
(=@MainActor (Double) -> Void=) as a parameter into a generic helper crashes
=swift-frontend= while emitting the reabstraction thunk — only in a whole-module
Release build, so a Debug build looks fine. =FilterRowView= therefore names
*which* parameter a cell edits with an enum and writes its closures inline, where
they inherit the view's own isolation and no thunk is produced. If a similar
crash appears elsewhere, that is the shape to look for.

* Formatting

*swift-format*, Apple's own, which ships inside the Xcode toolchain: =xcrun
swift-format=, no Homebrew, no package dependency, nothing for CI to install.
It is also the formatter behind Xcode's own Editor ▸ Structure ▸ Format
commands, so the editor and the command line agree by construction.

It is not the same tool as *SwiftFormat* (Nick Lockwood's), which is
third-party and configured completely differently. Installing "swiftformat" from
Homebrew gets the other one.

=.swift-format= at the repository root holds the configuration; Xcode discovers
it automatically by walking up from the file being edited. It is not the tool's
defaults: four-space indentation and a hundred-column limit are the codebase's
existing conventions, measured before being written down — the defaults are two
spaces, which would have rewritten every line in the project for no reason.

=make lint= runs with =--strict=, so any finding is a non-zero exit and CI fails
on it.

*One file opts out.* =BuiltInProfiles.swift= carries =// swift-format-ignore-file=
because its preset table is aligned by hand — eleven gains in columns, so one
preset can be compared with another by eye. The formatter collapses that
alignment into ordinary argument lists, and the table stops being a table. That
is a deliberate, documented exception rather than a disagreement with the tool.

*On SwiftLint.* Not used, deliberately. It is a third-party binary that every
contributor and every CI runner would have to install, in a project whose one
boast is that it has no dependencies at all. swift-format's lint mode already
covers the naming and style rules =AlwaysUseLowerCamelCase=,
=TypeNamesShouldBeCapitalized=, =NeverUseForceTry=, =DontRepeatTypeInStaticProperties=,
=ValidateDocumentationComments= and the rest. What SwiftLint would add on top is
mostly complexity metrics and force-unwrap policing; the project has no force
unwraps outside tests, and a metric nobody has needed yet is not worth a
dependency.

*On =.editorconfig=.* Not used. Xcode does not read it — it has never supported
the format — so in an Xcode-only project it would be a second, silent copy of
the indentation and line-length settings that =.swift-format= already holds, free
to drift out of step with it. It earns its place the day someone edits this
project in VS Code or Vim, and not before.

* Design tokens

Every font in the app comes from =Theme.Font=, and every colour from
=.primary= / =.secondary= / =.tertiary= or from =Theme=. A view that writes
=.font(.system(size: 12))= is a bug in the same way an unformatted file is:
nothing will fail, and the app will drift.

It did drift. Before the tokens existed there were eight hardcoded point sizes —
9, 10, 11, 12, 13, 14, 17 — *and* three of the system's semantic styles
(=.callout=, =.caption=, =.headline=) used alongside them. Which one a view used
depended on when it was written, so the Settings panes had ended up a different
size from the window and from each other, and text people had to read was being
set at 9 and 10 points.

Ten roles, and adding an eleventh should feel like it needs an argument:

| =title=            | 17 semibold        | the app's name in About, and nothing else |
| =heading=          | 13 semibold        | the heading of a pane or a block          |
| =body=             | 13                 | row text naming something: a device, a preset |
| =label=            | 12                 | labels and controls — the app's default   |
| =labelEmphasized=  | 12 semibold        | a label titling the group beneath it      |
| =secondary=        | 11                 | supporting text, axis legends             |
| =value=            | 11 medium, mono    | a number that changes as it is dragged    |
| =valueEmphasized=  | 11 semibold, mono  | the same, where the number is the subject |
| =report=           | 11 monospaced      | the diagnostics report                    |
| =tick=             | 10 mono digits     | axis ticks, and nothing else              |

Two rules behind the table. *Eleven points is the floor for anything anyone
reads* — =tick= is below it because axis numerals are glanced at, never read, and
it is the only role allowed there. And *monospaced digits are for numbers that
change*: a value that updates during a drag makes the row twitch between glyph
widths otherwise.

Fixed point sizes rather than the semantic styles, which means CoreEQ does not
follow Dynamic Type. That trade was already made — the window, the menu and the
Settings panes are laid out to fixed sizes and would break — so the tokens make
it consistent rather than accidental. Revisiting it is a layout project, not a
typography one.

One exception, and it should stay the only one: =PowerToggleStyle= sizes its
glyph from the toggle's own diameter. That is icon geometry, not typography.

Colour is in better shape and only half tidied. Text uses the three system
hierarchies; the response curve and the block borders come from =Theme.signal=
and =Theme.blockBorder=. What has *not* been collapsed is opacity: there are
around a dozen distinct values in use for fills, borders and dimming, several of
which are probably meant to be the same number. Prefer an existing one over
inventing another, and the whole set is worth naming the way the fonts now are.

*Where model logic lives.* =ProfileManager= is the only observable object in
the model layer, and it is deliberately not where the thinking happens. The
preset collection is =PresetLibrary=, chain arithmetic is =FilterChain=, and what
a stored device slot *means* is =DeviceEQState.resolved(against:)=. All three are
value types with no actor, no defaults and no dependencies, so they can be built
and compared in a test directly — which is why =PresetLibraryTests= and
=FilterChainTests= need no fixture at all.

=PresetLibrary= is a struct rather than a second =ObservableObject= on purpose:
SwiftUI does not follow nested observation, so an observable inside the manager
would publish nothing to the views watching it. Held as a stored property, every
mutation republishes for free.

One top-level type per file, named after it — nested types stay with the
type that owns them (=AudioEngine.Status=, =MenuRowView.Accessory=), and
extensions on foreign types live in =Extensions/= as =Type+Feature.swift=.

The =CoreEQ/= folder is a synchronized group: dropping a new =.swift= file
anywhere inside it adds it to the target automatically (and any other file
type becomes a bundle resource), no project-file edits needed. The
subfolders are plain groups, not folder references, so resources are copied
flat into =Contents/Resources/= regardless of which folder they live in.

Note that stale =membershipExceptions= paths are not merely ignored: Xcode
still resolves them as file references, and a moved file whose old path is
left behind fails the build with “Multiple commands produce …”.

The shipped icon files are generated from the SVG sources in =design/= by
=make icons= (requires ImageMagick: =brew install imagemagick=). After

- =CoreEQ/Resources/AppIcon.icon= — an Icon Composer document (background fill +
  =Assets/bars.svg= layer) compiled by =actool= into =Assets.car= during

* Architecture

This section is how CoreEQ is put together. *Why* it is put together this way —
one chain behind two editors, what a band is, what the graph is allowed to do —
is [[file:ARCHITECTURE.org][ARCHITECTURE.org]]. Read that before changing anything about the
relationship between the graphic and parametric editors.

** Audio path: how CoreEQ attaches to system audio

Implemented in =AudioEngine.swift=:

1. *Process tap.* The engine creates Core Audio process taps
   (=AudioHardwareCreateProcessTap=, macOS 14.2+) covering every process
   except CoreEQ itself — excluding itself prevents a feedback loop. One tap
   per output stream, because a tap binds to a single stream and takes its
   format. Once capture is proven the taps use
   =muteBehavior = .mutedWhenTapped=, so the tapped processes' original audio is
   silenced at the hardware and the only signal reaching the speakers is what
   CoreEQ writes back. Until then they are unmuted — see *Proving the tap*.
2. *Private aggregate device.* The tap and the current default output device
   are combined into a private (invisible) aggregate device with drift
   compensation, so tap input and device output share one IO cycle.
3. *IO proc.* An IO proc on the aggregate receives the tapped system mix each
   cycle, runs it through =EQProcessor=, and writes it to the real device's
   output buffers.

*** Proving the tap

A tap is created *unmuted*, and the render path writes nothing, until the engine
has seen it deliver a non-zero sample. Only then does it rebuild with
=.mutedWhenTapped= and start processing.

This is not caution for its own sake. =AudioHardwareCreateProcessTap= returns
success when the user has refused permission — measured, not assumed: with a
refusal recorded, the engine reported =status: running=, a two channel
device-bound tap, and not one sample. Muting on the strength of that gives a
completely silent Mac with every layer of the app reporting that it works, which
is the worst state this engine has.

Unmuted, the same refusal costs only that the audio is not equalized. That is
how an equalizer should fail, and it is why the order matters: prove, then mute.

The proof is polled every 250 ms and gives up after ten seconds, at which point
the engine says it is not capturing and *leaves the audio alone*. Returning to
the app after a refusal starts a fresh attempt, which is how allowing the
permission in System Settings takes effect — audio capture has no permission API
to consult, so coming back is the only signal available.

=EQProcessor.hasReceivedAudio= is the observation, and it is reported in
Settings ▸ Diagnostics alongside whether the tap is muting yet. The two have to
be read together: not capturing *while muting* is a silent Mac; not capturing
*while unmuted* is CoreEQ standing aside.

Because the tap dies with the process, a crash or quit always returns the
system to normal, unprocessed audio — there is no persistent driver state to
clean up.

** DSP

=EQProcessor= is one flat cascade of RBJ audio-cookbook biquads (transposed
direct form II, independent state per filter and channel; up to
=EQProcessor.maxFilters= entries, stereo). It has no notion of bands, sliders,
or lists: it is handed a chain and runs every entry the same way, which is what
makes the graphic and parametric editors two views of one equalizer rather than
two equalizers in series.

Coefficients come from =Biquad=, the same type =FrequencyResponseView= draws
its curve from. That sharing is deliberate and load-bearing — a second copy of
the gain law or the Nyquist guard would let the plot quietly disagree with what
is being heard.

Custom biquads were chosen over wrapping Apple's EQ Audio Unit because they are
trivially realtime-safe inside a HAL IO proc and have no format negotiation
edge cases (the spec allows either).

** A trap: NSToolbarDelegate's methods are required

Swift presents all three =NSToolbarDelegate= methods as optional. =NSToolbar=
does not: assign a delegate that omits
=toolbar(_:itemForItemIdentifier:willBeInsertedIntoToolbar:)= and AppKit logs

#+begin_example
NERROR: invalid delegate <CoreEQ.AppDelegate: 0x…> (does not implement all
required methods), and so can not be used!
#+end_example

and then *discards the delegate* — =toolbar.delegate= reads back nil. Measured,
not inferred. The consequence is silent: the identifier methods are never called,
no tracking separator is made, and the toolbar the sidebar's full-height layout
is defined against sits empty.

The item is built from the split view, and the toolbar is asked for its items
while the window is still being assembled, so =AppDelegate= holds the
=NSSplitViewController= rather than reaching for it through =mainWindow=, which is
not assigned yet at that point.

** A trap: publishing from inside a view update

A segmented =Picker= synchronises its selection while SwiftUI is updating the
view. Bind one to a =Binding= whose setter mutates an =ObservableObject= and the
mutation happens *during* that update — SwiftUI reports “Publishing changes from
within view updates is not allowed, this will cause undefined behavior”, and it
means it.

The A/B switcher hit this: its setter called =ProfileManager.setSlot=, which
swaps five published properties at once. The fix is not to defer with
=DispatchQueue.main.async=, which only moves the mutation somewhere unspecified —
it is to bind the control to local =@State= and apply the change in
=onChange=, which runs once the update has finished. A second =onChange= in the
other direction keeps the control in step when the model changes on its own,
which happens whenever the output device switches; =setSlot= ignores a request
for the slot already live, so the two cannot chase each other.

Two other =Picker=s exist. The editor tabs bind to =@AppStorage=, which is built
for exactly this. The parametric type column uses =.menu= style, whose selection
is written from a menu action rather than during layout. Neither has shown the
warning, but a new segmented picker bound to the manager would.

** Threading model

- The IO proc runs on the Core Audio realtime thread and *never blocks*:
  parameter changes (filters, preamp, bypass, sample rate) are staged behind an
  =OSAllocatedUnfairLock= and consumed with =lockIfAvailable()= — under
  contention the render path simply reuses the previous parameters for one
  cycle.
- It also never *allocates*. The staging chain is a fixed-length array of plain
  values, written in place, so handing over a new chain neither allocates on the
  main thread nor leaves the render thread holding the last reference to
  something it would then have to free inside the IO callback.
- Gain changes are smoothed over ~50 ms on the render thread, so profile
  switches and slider drags are glitch-free.
- Everything else (=AudioEngine=, =ProfileManager=, =SettingsStore=, UI) is
  =@MainActor=. =AppDelegate= wires =ProfileManager.$currentFilters= to
  =AudioEngine.apply(filters:)= via Combine, and =$currentPreamp= to
  =apply(preamp:)=.

** Resilience

- *Default output device changes* — a system-object property listener
  schedules a debounced engine rebuild on the new device.
- *Sample rate changes* — a listener on the aggregate device updates the
  filter coefficients (and resets filter state).
- *Sleep/wake* — =NSWorkspace.didWakeNotification= triggers a rebuild.
- *Startup failure* (typically missing permission) — up to three automatic
  retries, with the error surfaced in the menu and the main window.
- *Bypass* keeps the tap running and passes audio through untouched, so
  toggling is instant and glitch-free.

** Settings, About, and why they live in the status menu

=LSUIElement= makes CoreEQ an *accessory* application: no Dock icon, and no menu
bar of its own — not even while the main window is key. There is therefore no App
menu, which is where About, Settings, and Quit normally live, so the status menu
carries all three at its tail.

Three consequences worth knowing:

- *No ⌘,* — a status menu's key equivalents only fire while that menu is open, so
  a shortcut there would be a promise the app cannot keep.
- *Activate before showing anything.* An accessory app is not frontmost when its
  status menu is clicked, so both =SettingsOpener.open()= and =showAbout()= call
  =NSApp.activate(ignoringOtherApps:)= first or the window opens behind whatever
  is in front.
- *Opening the Settings scene needs SwiftUI.* =NSApp.sendAction(Selector(("showSettingsWindow:")))=
  no longer opens it, and returns =true= while doing nothing — a silent failure.
  =SettingsLink= and =EnvironmentValues.openSettings= are the supported routes and
  both live inside SwiftUI, so =SettingsOpener= hosts a one-point transparent view
  in the status item's button and keeps the action out of its environment.

  About is a tab of that window rather than =orderFrontStandardAboutPanel=. The
  panel is free and reads the name, version and copyright out of the bundle, so
  giving it up means owning those — =AboutSettingsView= reads the same two
  Info.plist keys for exactly that reason. What it buys is one surface instead of
  two, which matters more than usual here because an accessory app has no App
  menu and every surface needs its own way in.

  Both tabs are pinned to one size. A =TabView= sizes itself to whichever pane is
  showing, and a form and a short About block are nowhere near the same height, so
  switching made the window jump — which in a window this small is the most
  noticeable thing about it. Apple's own Settings windows do resize between panes,
  but between panes of comparable weight.

  The System Audio Recording row reports the *engine*, not a permission API,
  because there isn't one: nothing answers "may I tap system audio", and the only
  ground truth is whether the tap was created. That also lets it distinguish a
  refusal from a stopped engine instead of blaming the user for the latter.
  =EngineStatusBridge= carries that one fact across the scene boundary — the
  window is built by SwiftUI on its own schedule and cannot be handed an engine
  the app delegate creates lazily.

  =SettingsOpener.shared= is that way in for all three callers: the header's
  gear, the sidebar's app mark, and the menu row. A scene cannot be handed an
  argument, so =SettingsRoute= holds the destination tab and is set immediately
  before the window opens — deliberately not persisted, so the gear always means
  General and the app mark always means About.

  Two dead ends, both measured rather than assumed: a hosted =SettingsLink=
  contains no =NSButton= to =performClick=, because SwiftUI draws its own
  controls; and a hosting view belonging to no window never fires =onAppear=, so
  the action is never captured. The host must be a view that is really on
  screen — hence the status item's button rather than a window of our own.

About is =orderFrontStandardAboutPanel=, which reads the name, version and build
straight from the bundle — nothing to keep in step with the build.

=LoginItem= wraps =SMAppService.mainApp=, which registers the application itself
and so needs no helper bundle. It deliberately stores nothing: macOS owns the
state, the user can revoke it in System Settings → General → Login Items while
CoreEQ is not running, and a cached =Bool= would then be describing a world that
no longer exists.

** Why there is no volume control

Twice now a volume slider has been added and removed, so the reasoning is here to
stop it happening a third time.

Every actual equalizer has exactly one level control and it is not a volume. A
hardware graphic EQ — dbx 231, Klark Teknik DN360, Behringer Ultragraph — has its
band faders and then a *Level* fader; parametric units (API 550, Pultec EQP-1A)
have an output gain. Plugin EQs match: Pro-Q has Output Gain, Logic's Channel EQ
has Global Gain. In-app equalizers match too: Apple Music and VLC have bands and a
preamp. That control is makeup gain for what the curve took away, and CoreEQ has
it — =EQProfile.preamp=.

Listening volume lives downstream, in another box: the amplifier, the monitor
controller, the master fader. The macOS apps that *do* ship a volume slider —
eqMac, Boom, SoundSource — are audio control centres rather than equalizers, and
their sliders are their own gain (often a boost past 100%), not a mirror of the
system's.

CoreEQ's would have been a mirror: a third copy of a control already on the menu
bar, the keyboard, and in Sound settings, sitting next to a gain control that
isn't the system's and looks identical. If a *boost* beyond the system maximum is
ever wanted, that is a different feature, and it belongs in =EQProcessor= as gain
rather than as a proxy for =kAudioDevicePropertyVolumeScalar=.

** Persistence

=SettingsStore= wraps =UserDefaults=. Two keys carry everything that matters:

- =userProfiles= — the presets the user made, as JSON. Shared across devices: a
  preset is a thing you own, not a property of a cable.
- =deviceStates= — a =DeviceEQState= per output device, keyed by the device's
  *persistent UID*. Which preset is playing, any unsaved edits to it, the
  preamp, and the Quick EQ tone positions all follow the hardware, the way
  volume does on macOS. =AudioDeviceID= is reassigned per boot and cannot key
  anything that outlives a session, which is why the UID is used.

=ProfileManager= is the only writer of =deviceStates=; every mutation funnels
through =persistDeviceState()=, so a new control cannot change the sound without
being remembered alongside the rest. The keys that predate the per-device model
(=activeProfileName=, =workingFilters=, =workingPreamp=, =quickToneControls=,
=customBandGains=) are read once at launch, migrated into the current device's
slot, and cleared.

** Design decisions

- *Deployment target 14.2, not 13.0.* The process-tap API is the only way to
  process all system audio without shipping a virtual audio driver; it was
  introduced in macOS 14.2.
- *Fixed band ladder, free filters on top.* Every profile carries the same
  eleven centre frequencies (the ISO octave ladder 32 Hz – 16 kHz plus 20 kHz,
  Q 1.41 ≈ one-octave bandwidth) as its first eleven entries, in slot order —
  =ProfileManager.normalized= guarantees it, so the slider strip can index
  straight into the chain. Anything after those eleven is a filter the user
  added, with its own kind, frequency, and Q. The Nyquist guard in =Biquad= sits
  at 0.47 × sample rate so the 20 kHz band stays active at a 44.1 kHz device
  sample rate.
- *The editor is a tab view, and its tabs live on its border.* A tab belongs on
  its container's edge: in the window header the switcher sat a window's height
  from the block it changed, and inside that block's heading row it was a control
  replacing its own container while sitting in it, which reads as a filter over
  the contents rather than a choice of them. On the border it is also the block's
  title, which is why neither editor carries a heading of its own — "Graphic" and
  "Band Levels" were two names for one thing. =View.borderLabel= mounts it, and
  lives beside =WindowBackground= because its whole trick is carrying that same
  material so it cuts the stroke instead of patching over it.

- *Bypasses are power buttons, and there are two kinds left.* A switch is the
  control for a preference; these take part of the chain out of the signal, which
  is a bypass, and the power glyph is what every equalizer already uses for one.
  =PowerToggleStyle= is a =ToggleStyle= rather than a =Button= on purpose — a
  button that merely looks like a toggle loses the state VoiceOver announces, the
  keyboard behaviour, and the traits. Two weights: the master carries a tinted
  well because it is the way back on and must be findable when the rest of the
  window is dimmed; a band's is a plain glyph, because a well on every table row
  would be a column of boxes competing with the values.

  The menu bar keeps a native =NSSwitch=. That surface is the system's, not
  CoreEQ's — the header is modelled on the Wi‑Fi menu's title-plus-toggle row —
  so the vocabulary there is the menu's rather than the equalizer's.

- *The per-editor bypasses are gone.* They existed to hear one half of the chain
  alone, which A/B now does better and at matched loudness. Their real cost was
  what they said: the architecture's claim is that Graphic and Parametric are two
  views of *one* chain, and a bypass per half states the opposite. They were also
  a trap, because the flag is saved — a half switched off and forgotten leaves
  sliders that move, redraw the curve, and change nothing audible.

  =normalized= now forces =isEnabled= true on every ladder filter. Without it a
  chain stored while the graphic half was bypassed would come back silent with no
  control left that could explain it, and a rung at 0 dB is identity anyway, which
  is what "off" meant for a band.

- *Automatic gain is a mode of the trim, and it averages rather than peaks.*
  =AutoGain.trim(for:)= samples the chain's response at 96 log-spaced points and
  returns the negative of the mean: equal weight per octave, which is pink
  weighting, which is roughly how music spends its energy. Peak-based trimming
  was considered and rejected — the peak is never below the average, so using it
  as a “ceiling” replaces the average in every case and leaves Bass Booster
  audibly quieter than what it is being compared against. Clipping is therefore
  not guaranteed away, and cannot be: CoreEQ sees the mix after every application
  has set its own level, so the headroom is unknowable.

  Every chain edit funnels through =ProfileManager.chainDidChange()=, which
  recomputes the trim when the mode is on and then persists. One funnel rather
  than a recomputation at each of the sixteen mutators, so a new way to edit the
  chain cannot forget to keep the trim in step.

- *A and B are two working states, not an undo.* Each holds a complete sound —
  preset, chain, trim, tone — so switching compares rather than reverts, and both
  belong to the output device like everything else unsaved. A slot reached for
  the first time starts as a copy of the one it replaces: the first switch has to
  be silent, or the control's opening move is to change the thing it exists to
  compare. In =DeviceEQState= the live slot stays at the top level and the other
  sits in =alternate=, which is what lets a state written before A/B decode
  unchanged — no alternate, and A live.

- *A band is moved into the parametric editor, never converted.* =Edit as
  Filter…= lifts a slot's filter out unchanged and leaves the slot at 0 dB,
  which is identity — the chain sums to exactly what it did before. The reverse
  is not offered, because fitting an arbitrary filter back onto a fixed ladder
  would be an approximation, and this application does not approximate what the
  user asked for.
