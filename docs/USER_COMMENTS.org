- But these bobbly bobbles and dips in the curve are just visual, right? Do you have options to change the approximation and interpolation? How do you calculate the frequency lets say between 8 and 16k where that weird dip is …
  R: Thanks for digging into this — I really appreciate the feedback, and I'm glad to improve how the app works. The bobbles aren't a drawing artifact, they're the real response. The graph doesn't approximate anything: it evaluates the actual filter math at ~160 points across the plot and sums them, using the exact same filter code the audio runs through. So what you see is what you hear. The dip between 8k and 16k comes from two things: - Each band is a bell about one octave wide, and the bands sit one octave apart. When two neighbours are boosted the same amount, their skirts cross a little low, so the total sags slightly halfway between them. That happens between every pair of bands. - The x-axis gives each of the 11 bands equal width, so 8k→16k (a full octave) gets the same space as 16k→20k (a third of an octave). The top end is stretched out, which makes that same small dip look much bigger than it is. Near 16–20k the filters also get distorted by the sample rate limit, deepening it further. No options for it yet — the bandwidth and the axis are both fixed. On my list: adjustable bandwidth per band, a proper log axis, and shelf filters for the top and bottom bands. Narrower bells would smooth the sum out; the trade-off is bands bleeding into each other.

- If you could build one without drivers, why there was never one before? Or what was you main different point?
  R: Fair question — it isn't cleverness on my part, it's timing. Apple only shipped the Core Audio process-tap API in macOS 14.2. Before that, capturing system output genuinely required a virtual audio device, because there was no supported way to read the system mix from userspace. So my main difference is mostly that I built on the new API instead of the old approach. The trade-off is it requires macOS 14.2 or later.
