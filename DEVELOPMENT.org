#+TITLE: CoreEQ — Developer Guide

Everything needed to build, run, test, and package CoreEQ, plus a tour of the
project structure and architecture. End-user documentation is in
[[file:README.org][README.org]].

* Toolchain

- Xcode *16 or later* (the project uses the folder-synchronized project
  format, =objectVersion 77=).
- macOS *14.2 or later* to run (the process-tap API does not exist earlier).
- No external dependencies — system frameworks only (SwiftUI, AppKit,
  CoreAudio, AudioToolbox, Combine, os).

If your active developer directory points at the Command Line Tools instead of
Xcode (=xcode-select -p= prints =/Library/Developer/CommandLineTools=), either
switch it once:

#+begin_src sh
sudo xcode-select -s /Applications/Xcode.app
#+end_src

or prefix every =xcodebuild= call with
=DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer=.

* Building

Open =CoreEQ.xcodeproj= in Xcode and build (⌘B), or from the command line:

#+begin_src sh
xcodebuild -project CoreEQ.xcodeproj -target CoreEQ -configuration Debug build
#+end_src

=make build= does the same for the Release configuration (see “Packaging and
releases” for all Makefile targets).

The app lands in =build/Debug/CoreEQ.app=. The build is ad-hoc signed
(=CODE_SIGN_IDENTITY=-=) with the hardened runtime disabled — fine for local
development, revisit for distribution (see “Packaging”).

* Running

#+begin_src sh
open build/Debug/CoreEQ.app
#+end_src

- CoreEQ is a menu bar app (=LSUIElement=): no Dock icon, look for the sliders
  icon in the menu bar.
- First launch triggers the macOS *System Audio Recording* permission dialog
  (the usage string comes from =NSAudioCaptureUsageDescription= in
  =Config/Info.plist=). Without the permission the tap cannot be created and
  the engine reports a failure in the UI, retrying up to three times.
- Note that TCC ties the permission to the code signature; rebuilding with a
  different signature may re-prompt.

Engine activity is logged through =os.Logger= (subsystem
=com.andreypudov.coreeq=). Follow it live with:

#+begin_src sh
log stream --predicate 'subsystem == "com.andreypudov.coreeq"' --level info
#+end_src

* Testing

=make test= runs =CoreEQTests=, a host-less logic bundle covering the filter
maths, the built-in profiles, =ProfileManager=, =SettingsStore=, the analyzer and
its ring buffer, the scroll handling, and the layout arithmetic that has no
runtime check. See “Packaging and releases → Tests” for how the target is
assembled.

Nothing in that suite touches audio hardware, so the parts that only exist at
runtime still need a manual pass after changes:

1. Build and launch; confirm the menu bar icon appears and the window's header
   shows no engine warning.
2. Play music; switch between *Flat* and *Bass Booster* — the change must be
   audible, immediate, and free of clicks.
3. Toggle the master switch — instant, glitch-free.
4. Drag a band slider — the sound tracks the slider smoothly and the curve
   follows it.
5. Switch the system output device (speakers → headphones) — processing resumes
   on the new device within ~1 s, *and that device's own preset loads*.
6. Quit and relaunch — preset, edits, and enabled state come back, per device.
7. Quit — system audio returns to the normal unprocessed path.

* Packaging and releases

The =Makefile= wraps the common flows (it also auto-selects the full Xcode
toolchain if =xcode-select= points at the Command Line Tools):

| =make build=   | Release build into =build/Release/CoreEQ.app=          |
| =make test=    | Run the =CoreEQTests= unit suite                       |
| =make install= | Build and install to =/Applications=                   |
| =make release= | Build and zip to =dist/CoreEQ-<version>.zip= (=ditto=) |
| =make clean=   | Remove =build/= and =dist/=                            |

*** Tests

=CoreEQTests= is a host-less logic bundle: it never launches the app or touches
audio hardware, so it runs anywhere, including CI. It covers the filter math,
the built-in profiles and Quick EQ weighting, =ProfileManager= (naming, rename,
delete fallback, persistence, band-ladder alignment), and the analyzer's ring
buffer.

Because the project uses =PBXFileSystemSynchronizedRootGroup=, the test target
takes the whole =CoreEQ/= folder *minus* an exclusion list. A new source file
joins the test target automatically — if it imports SwiftUI, AppKit, or
CoreAudio, add it to =membershipExceptions= in =project.pbxproj= or the test
build will fail. Those entries are paths relative to =CoreEQ/=, so they carry
the folder too (=UI/MenuBar/MenuBarController.swift=); moving a file between
folders means updating its entry.

** Cutting a release

CoreEQ is distributed unsigned (ad-hoc signature, no Apple Developer
account). The release pipeline is GitHub Actions
(=.github/workflows/release.yml=): pushing a tag matching =v*= builds
=make release= on a macOS runner and attaches the zip to a GitHub Release
with generated notes.

*The runner image is a user-visible choice.* AppKit decides which generation of
the macOS design an app renders in from the SDK it was *linked against*, not
from the macOS running it. Building 1.6 on the =macos-15= image (Xcode 16, SDK
15.5) shipped a binary that drew as a pre-26 app on every current Mac, while
local builds against the 26 SDK looked native — same commit, same version, two
different-looking apps. Both workflows therefore pin =macos-26=, and the release
job asserts the linked SDK out of =LC_BUILD_VERSION= before publishing. The
deployment target (=MACOSX_DEPLOYMENT_TARGET= 14.2) is set in the project and is
unaffected by any of this: a 26-SDK build still runs on macOS 14.2.

1. Bump =MARKETING_VERSION= (and =CURRENT_PROJECT_VERSION=) in the target
   build settings.
2. Commit, then tag and push:
   #+begin_src sh
   git tag v1.1
   git push origin v1.1
   #+end_src

Notes on unsigned distribution:

- Downloaded (quarantined) copies trigger Gatekeeper; users bypass it once
  via System Settings → Privacy & Security → *Open Anyway* or by clearing
  the quarantine attribute. Building from source avoids this entirely —
  local builds are never quarantined. Both paths are documented for users
  in [[file:README.org][README.org]].
- The System Audio Recording (TCC) permission is keyed to the code
  signature; ad-hoc signatures have no stable identity, so each shipped
  update re-prompts users for the permission.

** If a Developer ID account becomes available

Sign with hardened runtime and notarize; this removes the Gatekeeper
warning and the per-update permission re-prompts:

#+begin_src sh
xcodebuild -project CoreEQ.xcodeproj -target CoreEQ -configuration Release build \
  CODE_SIGN_IDENTITY="Developer ID Application: Your Name (TEAMID)" \
  ENABLE_HARDENED_RUNTIME=YES

ditto -c -k --keepParent build/Release/CoreEQ.app CoreEQ.zip
xcrun notarytool submit CoreEQ.zip --keychain-profile <profile> --wait
xcrun stapler staple build/Release/CoreEQ.app
#+end_src

The app is currently *unsandboxed*. App Store distribution would require
enabling the sandbox and revisiting the audio entitlements; direct
(Developer ID) distribution does not.

One top-level type per file, named after it — nested types stay with the
type that owns them (=AudioEngine.Status=, =MenuRowView.Accessory=), and
extensions on foreign types live in =Extensions/= as =Type+Feature.swift=.

The =CoreEQ/= folder is a synchronized group: dropping a new =.swift= file
anywhere inside it adds it to the target automatically (and any other file
type becomes a bundle resource), no project-file edits needed. The
subfolders are plain groups, not folder references, so resources are copied
flat into =Contents/Resources/= regardless of which folder they live in.

Note that stale =membershipExceptions= paths are not merely ignored: Xcode
still resolves them as file references, and a moved file whose old path is
left behind fails the build with “Multiple commands produce …”.

** Icons

The shipped icon files are generated from the SVG sources in =Design/= by
=make icons= (requires ImageMagick: =brew install imagemagick=). After
editing an SVG, rerun the target and rebuild:

- =Design/logo.svg= → =CoreEQ/Resources/AppIcon.icns= — rasterized at the ten
  standard sizes (16–1024 px) and packed with =iconutil=; referenced from
  =Config/Info.plist= via =CFBundleIconFile=. This is the *fallback* icon
  for macOS 14/15.
- =CoreEQ/Resources/AppIcon.icon= — an Icon Composer document (background fill +
  =Assets/bars.svg= layer) compiled by =actool= into =Assets.car= during
  the build (=ASSETCATALOG_COMPILER_APPICON_NAME=, =CFBundleIconName=).
  This is the *primary* icon on macOS 26+: without it the system shows the
  =.icns= scaled down on a dark backing plate (the legacy-icon treatment),
  and with it the system also derives the dark/tinted icon-style variants
  automatically. The bar geometry is duplicated from =Design/logo.svg=;
  keep them in sync when the design changes. Icon caches are aggressive —
  after replacing the app, =lsregister -f /Applications/CoreEQ.app= plus
  =killall iconservicesagent Dock Finder= forces a refresh.
- =Design/menubar.svg= → =CoreEQ/Resources/MenuBarIconTemplate.png= (18 pt) and
  =@2x= (36 pt) — a black-on-transparent copy of the logo's EQ bars.
  macOS renders it as a /template image/: only the alpha channel is used,
  recolored automatically for Light/Dark mode. Keep this SVG a solid
  single-color silhouette; =MenuBarController= falls back to an SF Symbol
  if the resource is missing.

* Architecture

This section is how CoreEQ is put together. *Why* it is put together this way —
one chain behind two editors, what a band is, what the graph is allowed to do —
is [[file:docs/ARCHITECTURE.org][docs/ARCHITECTURE.org]]. Read that before changing anything about the
relationship between the graphic and parametric editors.

** Audio path: how CoreEQ attaches to system audio

Implemented in =AudioEngine.swift=:

1. *Process tap.* The engine creates a global Core Audio process tap
   (=AudioHardwareCreateProcessTap=, macOS 14.2+) covering every process
   except CoreEQ itself — excluding itself prevents a feedback loop. The tap
   uses =muteBehavior = .mutedWhenTapped=, so the tapped processes' original
   audio is silenced at the hardware; the only signal reaching the speakers is
   what CoreEQ writes back.
2. *Private aggregate device.* The tap and the current default output device
   are combined into a private (invisible) aggregate device with drift
   compensation, so tap input and device output share one IO cycle.
3. *IO proc.* An IO proc on the aggregate receives the tapped system mix each
   cycle, runs it through =EQProcessor=, and writes it to the real device's
   output buffers.

Because the tap dies with the process, a crash or quit always returns the
system to normal, unprocessed audio — there is no persistent driver state to
clean up.

** DSP

=EQProcessor= is one flat cascade of RBJ audio-cookbook biquads (transposed
direct form II, independent state per filter and channel; up to
=EQProcessor.maxFilters= entries, stereo). It has no notion of bands, sliders,
or lists: it is handed a chain and runs every entry the same way, which is what
makes the graphic and parametric editors two views of one equalizer rather than
two equalizers in series.

Coefficients come from =Biquad=, the same type =FrequencyResponseView= draws
its curve from. That sharing is deliberate and load-bearing — a second copy of
the gain law or the Nyquist guard would let the plot quietly disagree with what
is being heard.

Custom biquads were chosen over wrapping Apple's EQ Audio Unit because they are
trivially realtime-safe inside a HAL IO proc and have no format negotiation
edge cases (the spec allows either).

** Threading model

- The IO proc runs on the Core Audio realtime thread and *never blocks*:
  parameter changes (filters, preamp, bypass, sample rate) are staged behind an
  =OSAllocatedUnfairLock= and consumed with =lockIfAvailable()= — under
  contention the render path simply reuses the previous parameters for one
  cycle.
- It also never *allocates*. The staging chain is a fixed-length array of plain
  values, written in place, so handing over a new chain neither allocates on the
  main thread nor leaves the render thread holding the last reference to
  something it would then have to free inside the IO callback.
- Gain changes are smoothed over ~50 ms on the render thread, so profile
  switches and slider drags are glitch-free.
- Everything else (=AudioEngine=, =ProfileManager=, =SettingsStore=, UI) is
  =@MainActor=. =AppDelegate= wires =ProfileManager.$currentFilters= to
  =AudioEngine.apply(filters:)= via Combine, and =$currentPreamp= to
  =apply(preamp:)=.

** Resilience

- *Default output device changes* — a system-object property listener
  schedules a debounced engine rebuild on the new device.
- *Sample rate changes* — a listener on the aggregate device updates the
  filter coefficients (and resets filter state).
- *Sleep/wake* — =NSWorkspace.didWakeNotification= triggers a rebuild.
- *Startup failure* (typically missing permission) — up to three automatic
  retries, with the error surfaced in the menu and the main window.
- *Bypass* keeps the tap running and passes audio through untouched, so
  toggling is instant and glitch-free.

** Settings, About, and why they live in the status menu

=LSUIElement= makes CoreEQ an *accessory* application: no Dock icon, and no menu
bar of its own — not even while the main window is key. There is therefore no App
menu, which is where About, Settings, and Quit normally live, so the status menu
carries all three at its tail.

Three consequences worth knowing:

- *No ⌘,* — a status menu's key equivalents only fire while that menu is open, so
  a shortcut there would be a promise the app cannot keep.
- *Activate before showing anything.* An accessory app is not frontmost when its
  status menu is clicked, so both =SettingsOpener.open()= and =showAbout()= call
  =NSApp.activate(ignoringOtherApps:)= first or the window opens behind whatever
  is in front.
- *Opening the Settings scene needs SwiftUI.* =NSApp.sendAction(Selector(("showSettingsWindow:")))=
  no longer opens it, and returns =true= while doing nothing — a silent failure.
  =SettingsLink= and =EnvironmentValues.openSettings= are the supported routes and
  both live inside SwiftUI, so =SettingsOpener= hosts a one-point transparent view
  in the status item's button and keeps the action out of its environment.

  Two dead ends, both measured rather than assumed: a hosted =SettingsLink=
  contains no =NSButton= to =performClick=, because SwiftUI draws its own
  controls; and a hosting view belonging to no window never fires =onAppear=, so
  the action is never captured. The host must be a view that is really on
  screen — hence the status item's button rather than a window of our own.

About is =orderFrontStandardAboutPanel=, which reads the name, version and build
straight from the bundle — nothing to keep in step with the build.

=LoginItem= wraps =SMAppService.mainApp=, which registers the application itself
and so needs no helper bundle. It deliberately stores nothing: macOS owns the
state, the user can revoke it in System Settings → General → Login Items while
CoreEQ is not running, and a cached =Bool= would then be describing a world that
no longer exists.

** Why there is no volume control

Twice now a volume slider has been added and removed, so the reasoning is here to
stop it happening a third time.

Every actual equalizer has exactly one level control and it is not a volume. A
hardware graphic EQ — dbx 231, Klark Teknik DN360, Behringer Ultragraph — has its
band faders and then a *Level* fader; parametric units (API 550, Pultec EQP-1A)
have an output gain. Plugin EQs match: Pro-Q has Output Gain, Logic's Channel EQ
has Global Gain. In-app equalizers match too: Apple Music and VLC have bands and a
preamp. That control is makeup gain for what the curve took away, and CoreEQ has
it — =EQProfile.preamp=.

Listening volume lives downstream, in another box: the amplifier, the monitor
controller, the master fader. The macOS apps that *do* ship a volume slider —
eqMac, Boom, SoundSource — are audio control centres rather than equalizers, and
their sliders are their own gain (often a boost past 100%), not a mirror of the
system's.

CoreEQ's would have been a mirror: a third copy of a control already on the menu
bar, the keyboard, and in Sound settings, sitting next to a gain control that
isn't the system's and looks identical. If a *boost* beyond the system maximum is
ever wanted, that is a different feature, and it belongs in =EQProcessor= as gain
rather than as a proxy for =kAudioDevicePropertyVolumeScalar=.

** Persistence

=SettingsStore= wraps =UserDefaults=. Two keys carry everything that matters:

- =userProfiles= — the presets the user made, as JSON. Shared across devices: a
  preset is a thing you own, not a property of a cable.
- =deviceStates= — a =DeviceEQState= per output device, keyed by the device's
  *persistent UID*. Which preset is playing, any unsaved edits to it, the
  preamp, and the Quick EQ tone positions all follow the hardware, the way
  volume does on macOS. =AudioDeviceID= is reassigned per boot and cannot key
  anything that outlives a session, which is why the UID is used.

=ProfileManager= is the only writer of =deviceStates=; every mutation funnels
through =persistDeviceState()=, so a new control cannot change the sound without
being remembered alongside the rest. The keys that predate the per-device model
(=activeProfileName=, =workingFilters=, =workingPreamp=, =quickToneControls=,
=customBandGains=) are read once at launch, migrated into the current device's
slot, and cleared.

** Design decisions

- *Deployment target 14.2, not 13.0.* The process-tap API is the only way to
  process all system audio without shipping a virtual audio driver; it was
  introduced in macOS 14.2.
- *Fixed band ladder, free filters on top.* Every profile carries the same
  eleven centre frequencies (the ISO octave ladder 32 Hz – 16 kHz plus 20 kHz,
  Q 1.41 ≈ one-octave bandwidth) as its first eleven entries, in slot order —
  =ProfileManager.normalized= guarantees it, so the slider strip can index
  straight into the chain. Anything after those eleven is a filter the user
  added, with its own kind, frequency, and Q. The Nyquist guard in =Biquad= sits
  at 0.47 × sample rate so the 20 kHz band stays active at a 44.1 kHz device
  sample rate.
- *A band is moved into the parametric editor, never converted.* =Edit as
  Filter…= lifts a slot's filter out unchanged and leaves the slot at 0 dB,
  which is identity — the chain sums to exactly what it did before. The reverse
  is not offered, because fitting an arbitrary filter back onto a fixed ladder
  would be an approximation, and this application does not approximate what the
  user asked for.
